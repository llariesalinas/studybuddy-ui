### Gotchas (these bit me — save yourself the time)
- **`faker` is NOT pinned** in `backend/requirements.txt` but `seed_data.py` imports it. I installed `faker==40.20.0` into the venv. Consider pinning it (dev dep).
- **`.git/index.lock` keeps reappearing** (an IDE's git integration). If a git command fails with "Unable to create index.lock", `Remove-Item .git\index.lock -Force` and retry. No git process is actually running.
- **Never `git add -A` / never `git add` a whole shared file blindly.** The working tree has the user's **in-progress password-reset/OTP feature** spread across `views.py`, `settings.py`, `models.py`, `tests.py`, `Login.vue`, `Register.vue`, etc. Always `git add <specific files you changed>` and check `git diff --stat` first. (I once swept their WIP into a commit and had to surgically separate it.)
- **PowerShell here-strings mangle f-strings/quotes.** For multi-line Python diagnostics, write a temp `.py` file and run it, then delete it. For git commits, use multiple `-m` flags (no inner double-quotes).

### Verification patterns that worked well (no test suite for most areas)
- Backend endpoint logic without a server: DRF `APIRequestFactory` + `force_authenticate`, call the view function directly, read `resp.status_code` / `resp.data`.
- Query-count / N+1 measurement: `django.test.utils.CaptureQueriesContext(connection)`.
- Mutating tests without persisting: wrap in `with transaction.atomic(): … ; transaction.set_rollback(True)`.

## 3. Chat bug #1 — conversations not showing (FIXED, `dc0d951`)
`/chat/rooms/` 500'd whenever a room contained a **system message with `sender=None`** (the support-ticket feature posts these: "Ticket #N created…", "marked as Resolved"). `MessageSerializer.get_sender_name`'s `except` branch re-dereferenced `obj.sender` and re-raised `RelatedObjectDoesNotExist`, killing the whole list; the frontend caught the 500 and showed no conversations. Fixed `get_sender_name` (`chat/serializers.py`) and `serialize_message_payload` (`chat/services.py`) to fall back to `"System"`. Verified: all users with rooms now return 200.

## 4. Chat bug #2 — ~5s load (FIXED, `fd89af3`)
`ChatRoomSerializer` was a severe N+1 (~10 queries/room): `get_last_message`, `get_unread_count`, `get_current_booking_context`, and `get_partner_context` (which **redundantly re-ran** `get_current_booking_context`). Fixes:
- Removed `partner_context` from the **list** (the sidebar never shows it). It's now served by a new **`GET /chat/rooms/<id>/`** detail endpoint (`get_room_detail`), loaded non-blocking on room open via the new store action `fetchRoomDetail` (called in `selectRoom`).
- Batched `unread_count` (one aggregate) and `last_message` (subquery for latest ids + one fetch) in `list_chat_rooms`, passed to the serializer via context maps (`unread_map`, `last_message_map`, `skip_partner_context`).
- `get_partner_context` now accepts a precomputed `current_booking` (sentinel `_CURRENT_BOOKING_UNSET`) so it doesn't recompute; serializer memoizes current_booking per room (`_booking_ctx_cache`).
- Measured: **30 → 13 queries** for 3 rooms (10 → 4.3/room); bigger win at scale.

## 5. OPEN ITEMS / landmines (next AI: prioritize these)

### Data-integrity / schema drift (high value — investigate)
1. **`ChatRoom.room_type` drift.** DB table `studybuddy_chatroom` has a **NOT NULL `room_type`** column, but the `ChatRoom` model (`chat/models.py`) has **no such field**. → `get_canonical_room()`'s `ChatRoom.objects.create(...)` **fails with IntegrityError** whenever a canonical room must be auto-created. This breaks chat-room creation paths used by `approve_booking` / `reject_booking` / booking creation / `start_inquiry_chat` (seeded rooms exist only because seed inserts them differently). I shielded **cancellation** from it (`0e4547e` made its booking-event non-fatal), but the **root drift is unfixed**. Likely an unmigrated/edited migration. Check `backend/studybuddy/migrations/` for `room_type` and reconcile model↔DB.
2. **`Message.sender` drift.** Model declares `null=False`, but DB column is **nullable** and the support-ticket feature inserts null-sender messages. Reconciling the model to `null=True` (with a migration) would make intent explicit. (Serialization is already null-safe after `dc0d951`.)
3. **`ChatRoom` with a null participant.** At least one room has `tutee_id` or `tutor_id` = NULL. `get_tutee_name`/`get_tutor_name` deref `obj.tutee`/`obj.tutor` and would 500 the list for the other participant. Worth cleaning up + guarding.

### Chat performance — further headroom (optional)
- `current_booking` is still ~3 queries/room (sidebar status chip needs it). Batching `get_current_booking_context` across rooms is the next lever but a larger refactor.
- **Pagination was deliberately skipped** — a silent cap would re-hide conversations (the exact bug we fixed); real pagination needs frontend infinite-scroll. Only worth it if users get hundreds of conversations.
