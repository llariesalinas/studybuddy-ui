Async Email Architecture

How StudyBuddy's email system is being hardened: a background queue (Django-Q2), a central mailer service, and a hybrid model that keeps login honest while moving everything else off the request thread. This page explains the design before it's built — click through the tabs.

The problem we're solving

Email is currently sent inside the web request. That couples user-facing actions to a third party (Gmail) that can be slow or down.

#WeaknessConsequence
1OTP email sent synchronously inside loginGmail slow/down → every login stalls then 500s. A single point of failure.
2No retry on transient SMTP errorsOne hiccup fails the whole operation.
3Failures only logged; reset/notice fail silentlyNo visibility — you can't tell mail was dropped.
4Only an IP-based rate limitAbuse can drain Gmail's ~500/day quota.
5Plain-text onlyLooks unprofessional; weaker deliverability.
The core idea Put a queue between "something happened" and "send the email." The web request just drops a job on the queue and returns instantly; a separate worker process delivers the mail, retries on failure, and records what happened.

The moving parts

Each piece has one job. Hover/read the cards, then expand for detail.

⚡ Django-Q2

The task queue library. Lets you say "run this function later, in the background."

🗃 ORM broker

Where queued jobs are stored: your existing database. No Redis to install or run.

⚙ qcluster worker

A separate process (manage.py qcluster) that pulls jobs and runs them.

✉ mailer.py

One module all email goes through. Renders templates, sends, retries, records.

📋 EmailSendLog

A DB table logging every send (ok/failed). Powers the per-account cap + auditing.

🎨 Email templates

Paired .html + .txt files per email, rendered to branded mail.

Why a dedicated mailer.py instead of sending from the views?

Today the send_* helpers live in views.py. Centralizing them means one place owns retries, logging, templates, and the cap — the views just say what to send, not how. It also matches the project rule of routing external calls through one service layer.

Gotcha: don't name it email.py A module named email.py inside the app package shadows Python's built-in email module, which Django's mail code imports — it breaks sending in confusing ways. We name it mailer.py.
What does an async task function look like? 
# studybuddy/mailer.py
def send_password_reset_email_task(user_id):   # runs in the worker
    user = User.objects.get(pk=user_id)         # re-fetch (args must be serializable)
    text, html = _render("email/password_reset", {"url": reset_url(user)})
    _deliver("Reset your password", text, html, [user.email])

# studybuddy/views.py  -> just enqueue, return immediately
async_task("studybuddy.mailer.send_password_reset_email_task", user.id)

The view never waits for Gmail. The worker picks the job up a moment later.

The hybrid model: why OTP is different

"Make everything async" sounds clean, but OTP breaks the rule — the user is staring at the screen waiting for that code.

EmailPathWhy
Login OTPsync, hardenedUser is waiting for it. If it truly can't send, they deserve an immediate, honest error — not a silent queue.
Password-reset linkasyncUser already saw "check your email." A few seconds' delay is fine.
Password-changed noticeasyncPurely informational. Never block on it.
The trap we avoided If OTP were async and the worker were down, login would say "code sent" but the code never arrives — with no error. The user is stuck. Keeping OTP sync means a real failure surfaces right there as a 500 they can retry.

"Hardened" sync means:

# short timeout so a hung SMTP can't freeze login for long
get_connection(timeout=8)
# a couple of quick retries for transient blips
for attempt in range(3): try send; except: backoff & retry
# final failure -> raise -> login_view returns an honest 500

Resilience & guardrails

Retries (async)

Django-Q2 re-runs failed jobs automatically. We cap attempts so a permanently broken send doesn't loop forever, and failed tasks are kept for inspection.

# settings.py
Q_CLUSTER = {
    "name": "studybuddy",
    "orm": "default",        # use the DB as the broker
    "retry": 90,            # seconds before a failed job is retried
    "max_attempts": 3,
    "catch_up": False,     # don't replay a backlog after downtime
    "save_limit": 250,      # keep recent task history
}

Per-account send cap (#4)

On top of the existing per-IP throttle, we count rows in EmailSendLog for a given recipient in the last hour. Over the limit → we refuse and return 429. This protects the Gmail daily quota from a single abused address.

Why a DB table, not a cache counter? There's no shared cache configured — Django's default is in-memory and per-process. The web server and the worker are different processes, so a memory counter wouldn't agree between them. The database is the one source both share.

Failure visibility (#3)

Two layers: Django-Q2 keeps failed tasks in its own table, and every attempt writes an EmailSendLog row (status + error). No more silent drops on password-reset.

Why Django-Q2 (and not Celery)?

Django-Q2 chosenCelery + Redis
BrokerYour existing DBNeeds a running Redis server
Extra services1 worker processRedis + worker
Windows devRuns cleanlyFiddly (--pool=solo)
Power/scale ceilingPlenty for this appHigher, but unneeded here
Ops burdenLowHigher

For StudyBuddy's scale and a Windows dev setup, Django-Q2 gives async + retries without standing up and babysitting a Redis instance. Celery would be the pick at much larger scale or with heavy scheduling needs.

Running & debugging

Start the worker (dev)

# terminal 1 - the web server
python manage.py runserver
# terminal 2 - the queue worker (REQUIRED for async mail)
python manage.py qcluster
Most common "why didn't my email send?" The qcluster worker isn't running. Async jobs pile up in the DB and wait. Login OTP still works (it's sync) — which is exactly why we kept it that way.

Inspecting failures

  • Django admin → Django Q → Failed tasks shows async jobs that errored.
  • EmailSendLog table shows every send attempt with status + error text.
  • App logs still capture hard failures via logger.exception.

In DEBUG with no SMTP configured

The transport ladder falls back to the console backend, so the worker just prints the email to its terminal — you can test the whole queue path without sending a single real message.
