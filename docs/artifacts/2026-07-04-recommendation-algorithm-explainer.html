Overview

Studybuddy ranks tutors for a tutee using a hybrid recommender: a weighted blend of two independent scores.

CBF — Content-Based Filtering How well the tutor's subjects, expertise, course, year level, and teaching level match the tutee's profile.

CF — Collaborative Filtering Whether tutees with similar rating history rated this tutor well (Pearson correlation, k-nearest-neighbor).

hybrid_score  =  0.7 × CBF  +  0.3 × (CF / 5)

Source: backend/studybuddy/recommender/hybrid.py:31

Before either score is computed, a tutor has to survive several hard gates — institution match, subject match, mode/budget, and (for the search flow) date/time availability. Gates run first; scoring only ranks whoever is left.

SCORING
Hybrid ranking of whoever survived the gates
Every remaining candidate gets a CBF score and a CF score, blended 70/30, then sorted descending. See below for both formulas.

Hybrid score formula

hybrid_score  =  (0.7 × cbf_score)  +  (0.3 × (cf_score / 5))

CBF score is already normalized to a 0–1 range. CF score is a predicted star rating (roughly 1–5), so it's divided by 5 before blending so both terms are on the same 0–1 scale.

If a tutee has no rating history at all (cold start — no Rating rows), cf_score defaults to 0, so ranking degrades gracefully to pure CBF (content match) rather than crashing.

How each sub-score is computed

Sub-scoreFormula
s_subject1 if the tutor teaches any subject in the tutee's subject list (preferences + requested subject), else 0
s_expertiseaverage(tutor's expertise_level across matching subjects) / 5  (0 if no match)

s_level1 normally; forced to 0 if tutor's teaching_level == "SHS" but the tutee is college level (year_level > 12)
score = 0.35·s_subject + 0.20·s_expertise + 0.20·s_course + 0.15·s_year + 0.10·s_level

Catalog-awareness: how get_student_subject_codes filters preferences

Before matching, the CBF calls recognized_subject_codes_for_profile(student_profile) (subject_recognition.py) to get the set of subjects the institution has recognized for the student's course via InstitutionCourseCatalog. Only preference subjects that appear in that recognized set are passed into the scoring loop.

This means the Institution Course Catalog directly controls CBF matching. Adding a subject to a course's catalog makes it immediately scoreable; removing one silently drops it from the student's effective subject list — even if it is still saved in their Preference record. Subjects a user already has in their profile remain visible in preference-editing UI (via include_current=True) so they can remove them, but they contribute zero to their CBF score once derecognized.

CF — Collaborative Filtering (Pearson, k-nearest-neighbor)

recommender/CF.py

Built from every Rating row in the system: a sparse matrix {student_id: {tutor_id: rating_score}}.

1. Similarity between two tutees — Pearson correlation

sim(u,v) = Σ (ru,i−ū)(rv,i−v̄)  /  √Σ(ru,i−ū)² · √Σ(rv,i−v̄)²

Computed only over tutors both tutees have rated in common (common = ratings[u] ∩ ratings[v]). Returns 0 if they've never rated any tutor in common.

2. Top-k neighbors

top_k(ratings, student_id, k=5) — similarity against every other tutee with rating history, sorted descending, keep the top 5.

3. Predicted rating for a candidate tutor

predicted = student_avg +   Σ sim(u,neighbor)·(neighbor's rating − neighbor_avg)  /  Σ |sim(u,neighbor)|

Only neighbors who actually rated this specific tutor contribute. If none of the top-5 neighbors rated this tutor, compute_cf_score returns None → treated as 0 in the hybrid blend.

Cold-start tutees (no Rating rows at all) skip CF entirely — student_id not in ratings short-circuits to None. This is why a brand-new tutee's dashboard is really a pure-CBF ranking, weighted as if CF were 0.

Fields it reads

Rating.student Rating.tutor Rating.rating_score

Caching (dashboard path only)

recommender/dashboard.py

Dashboard recommendations are cached per-tutee for 10 minutes (CACHE_TTL_SECONDS = 600), keyed as dash_recs:v{version}:limit{n}:{tutee_id}.

A global cache version counter is bumped (invalidating all cached dashboard results at once) whenever something that could change rankings happens:

tutee saves preferences a rating is submitted a tutor edits their profile a tutor changes their subjects

If the cache backend (Redis) is down, reads/writes fail silently and the system falls through to a live recompute rather than erroring — degraded, not broken.
