Institution-Scoped Tutor Matching

Tutees are now hard-filtered to see only tutors from their own institution across every recommendation and search surface. Cross-institution leakage is impossible at the query level.

Branch: feature-sidebar-redesign Backend only — no frontend changes Tests: 10 added · all pass No migrations Final review: Approved
What this plan fixed
Before

A CPU tutee could receive recommendations for tutors registered under any institution. All three API surfaces — FindTutors, dashboard widget, and search — queried the entire Tutor table with no institution check. There was no enforcement, only the UI's assumption that users would only see "relevant" tutors.

After

Every tutor queryset is institution-scoped before any other filter runs. A null-institution tutee gets an empty list (not an error). A null-institution tutor is auto-excluded by SQL semantics. The fix is in the data layer — the UI doesn't need to change because it can't receive cross-institution data.

Core Helper

One function, one responsibility. Every entry point imports and calls this.

backend/studybuddy/recommender/utils.py — new file

def filter_tutors_by_institution(queryset, student_profile): institution_id = student_profile.institution_id # raw FK — no JOIN if institution_id is None: return queryset.none() # tutee unassigned → empty, not error return queryset.filter(profile__institution_id=institution_id) # Tutors with institution=None are auto-excluded: SQL NULL=value is never true
Why institution_id not institution__id? Using the raw FK column avoids a JOIN to the partner_institutions table that Django would otherwise generate. The result is identical but one query level cheaper per recommendation call.

Affected Endpoints

POST /api/recommend-tutors/ FindTutors flow. Institution filter applied first in get_recommendation_candidate_tutors, before mode / budget / availability filters. Hybrid recommender then scores the already-scoped candidate set.
GET /api/recommendations/ Dashboard widget. Both paths filtered: main path (candidate_qs via subject preferences) and fallback path (_fallback when tutee has no preferences). Cache key already scoped per tutee — no cross-tutee cache pollution.
GET /api/search-tutors/ Previously unauthenticated (no permission_classes). Now requires IsAuthenticated and institution-scopes results. Had no frontend caller but was a live endpoint accessible via direct API call.

Edge Cases & Invariants

ScenarioBehaviour
Tutee has institution = None Empty list returned (200 OK). Admin must assign institution before matching works. Not an error.
Tutor has institution = None Auto-excluded by SQL: NULL = value is never true. Invisible to all tutees until admin assigns.
Admin / SuperAdmin accounts Flagged is_domain_exempt; never in the tutor pool. No special handling needed.
Dashboard fallback (no preferences) Fallback now scoped — previously returned random cross-institution tutors when tutee had no subject preferences.
New institution onboarded Add a row to partner_institutions. No code change needed. Users registered under the new domain are automatically scoped.
Multi-institution scale Single database, multi-tenant by FK. Per-institution databases not needed unless a legal data-residency contract requires it.

Before You Deploy

Check for null-institution accounts Run this in the Django shell before enabling on production. If the count is non-zero, those users will immediately get empty recommendation lists.
UserProfile.objects.filter( role__in=['Tutee', 'Tutor'], institution=None, ).count() # Should be 0, or a known number you've accounted for. # Coordinate with institution admin to backfill if non-zero.
