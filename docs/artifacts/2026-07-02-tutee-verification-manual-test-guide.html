Tutee Enrollment Verification — Manual Test Guide

Covers Phases 1–3, which are shipped on feat/tutee-enrollment-verification. Check off each case as you verify it in the browser; progress is saved locally in this file.

Phase 4 (email notifications + SuperAdmin dev tools) is still a Draft plan — not implemented — so it is intentionally not covered here. See docs/plans/2026-07-01-tutee-verification-phase4-email-devtools.md.

Setup

  • Backend: python manage.py runserver (from backend/)
  • Frontend: npm run dev (from repo root)
  • Seed data if the DB is empty: python manage.py seed_data
  • You need at least one Tutee account, one Tutor account, and one Admin (or SuperAdmin) account. Use Django admin (/admin/) or manage.py shell to inspect/adjust UserProfile.role, TuteeApplication, and TutorApplication rows directly when a test needs a specific state.
  • To simulate lapse/renewal without waiting 90 days, backdate reviewed_at on the relevant TutorApplication/TuteeApplication (or its latest approved DocumentRenewalReview) via the Django shell — this is what Phase 2's browser verification used.
  • To test the enforcement grace period, toggle TUTEE_VERIFICATION_ENFORCEMENT_START_DATE in backend/.env (unset or future date = grace period active; past date = enforced) and restart the backend.

Phase 1 — Data model

Backend / Django admin
  1. Open /admin/ (Django admin), log in as a superuser.
  2. Confirm Tutee applications and Tutee document renewal reviews appear as separate model tables, alongside the existing Tutor equivalents.
Expect: both tutee tables exist and are independently browsable/editable, mirroring the tutor tables' fields (status, reviewed_by, reviewed_at, reminder_7day_sent_at, reminder_1day_sent_at, enrollment_proof).

Phase 2 — Booking gate

Full stack
  1. Set TUTEE_VERIFICATION_ENFORCEMENT_START_DATE to a past date (e.g. 2020-01-01), restart backend.
  2. Log in as a Tutee with no approved TuteeApplication (fresh account or one whose application is pending/rejected).
  3. Attempt POST bookings/confirm/ via the booking flow UI.
Expect: request is rejected with 403 and a verification_required code; the UI surfaces a message pointing at verification, not a generic error.
  1. Unset TUTEE_VERIFICATION_ENFORCEMENT_START_DATE (or set it to a future date), restart backend.
  2. Log in as a Tutee with no TuteeApplication at all.
  3. Complete a booking through to confirmation.
Expect: booking succeeds — no verification block while the grace period is active.
  1. Backdate an approved tutor's renewal clock (reviewed_at on the latest approved renewal review, or the application itself) by more than 90 days via shell/admin.
  2. Log in as that tutor. Navigate around the app (dashboard, profile, messages, etc.) — no forced redirect.
  3. Attempt POST bookings/<id>/approve/ on a pending booking request.
Expect: free navigation everywhere (the global lockout only applies to never-approved tutors); the accept action itself returns 403 with wording that does not say "renew" if the tutor was never approved, or correctly references renewal if they were previously approved and lapsed.
  1. Log in as a tutor whose TutorApplication has never been approved (pending or rejected, no prior approval history).
  2. Try navigating to any authenticated route other than /application-status.
Expect: router redirects to /application-status (the router-level lockout is narrowed to this case only, per Phase 2).

Phase 3 — Application status UI & admin queue

Frontend
  1. Log in as a Tutee with no TuteeApplication yet.
  2. Navigate to /application-status.
  3. Submit school ID + enrollment proof through the first-submission form (not the resubmit form).
Expect: a genuine first-submission path is shown (distinct from tutor registration, since tutees don't submit documents at signup); after submit, status flips to pending and the page reflects it without a full reload.
  1. Visit /application-status as a Tutor with a pending/rejected application, then as a Tutee in the same state.
Expect: same route/component serves both roles with role-correct copy and actions (resubmit for existing applications, first-submission for tutees with none).
  1. Visit TuteeProfile.vue (tutee's own profile) — confirm the verification status card appears with the correct current status/renewal due date.
  2. Visit TutorProfile.vue — confirm the same card appears, and that the previously-hardcoded "Verified" badge is now conditional (does not contradict the card when the tutor is actually unverified/due).
Expect: no conflicting verification signals on either profile page.
  1. Log in as Admin or SuperAdmin, go to /admin/tutor-applications.
  2. Confirm two tabs: Tutors and Tutees.
  3. Switch to the Tutees tab — confirm it lists tutee submissions (not tutor rows), with columns matching the tutor tab's shape (status, renewal due date, etc.).
Expect: tutor tab behavior is unchanged from before Phase 3; tutee tab is populated and independently filterable.
  1. On the Tutees tab, open a pending application's detail offcanvas.
  2. Approve one tutee application; reject another (with a reason).
Expect: status updates reflect immediately in the queue; the tutee sees the new status on their own /application-status page and profile card on next load.
  1. Get a tutee into a "renewal due" or "renewal pending" state (backdate renewal clock, then have the tutee resubmit documents).
  2. As Admin, approve or reject the renewal submission from the admin queue.
Expect: renewal status updates correctly, dedup/reminder fields reset on approval, and the tutee's profile card reflects the new due date.
  1. With enforcement active (past cutover date) and a tutee with no approved application, try navigating directly to a booking-flow route (e.g. Find Tutors / Initial Booking).
  2. Repeat with enforcement inactive (grace period) — same tutee, same route.
Expect: blocked (redirected) when enforced and unverified; allowed during the grace period.
