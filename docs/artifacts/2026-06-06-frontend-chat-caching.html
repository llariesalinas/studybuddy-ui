Frontend and chat caching

A frontend-first caching rollout to make stable catalog pages and the messaging experience feel faster. This artifact explains the reason, tech stack, affected code areas, and implementation path before and after the change lands.

Status Approved
Date 2026-06-06
Source docs/plans/2026-06-06-frontend-chat-caching.md

What This Improves

Catalog data

Reference lists load once per TTL

Subjects, courses, institutions, payment methods, and receiving institutions can reuse session cache instead of repeating the same GET calls on every visit.

Messaging

Chats render immediately on revisit

Recent rooms and room history are restored from sessionStorage first, then refreshed through REST and WebSocket updates.

Safety

Short-lived and user-scoped

Cache keys include the user id, chat bodies stay in sessionStorage only, and logout clears sb-* session entries.

Why We Need It

Repeated reference requests

Several pages ask for the same stable lists: subjects/, courses/, partner-institutions/, and payment-methods/. Those values do not change minute to minute, so repeatedly blocking screens on the same network calls wastes time.

Slow perceived chat loading

Messages feel slow when the user revisits a conversation and the UI waits for REST history before showing anything. The better experience is to show the recent session cache immediately, then quietly sync newer messages.

Tech Stack Purpose

sessionStorage

Short-lived browser cache

Chosen because chat bodies should not persist forever. Data disappears when the browser session ends and is cleared on logout/user switch.

Pinia

Shared frontend state

Catalog and chat data already live naturally in stores, so Pinia keeps cached results reusable across views without adding a new state framework.

Axios helper

One cache contract

A dedicated cachedGet wrapper keeps TTL, user scoping, path normalization, and in-flight dedupe in one place instead of scattering cache logic through Vue pages.

Django REST

Incremental history

The backend keeps the same history endpoint but accepts after_id so the frontend can fetch only messages newer than the cached high-water mark.

WebSocket

Live reconciliation

Existing live chat events continue to be the freshest source for new messages, read receipts, room updates, and booking context changes.

Vitest

Cache behavior tests

Cache bugs are subtle, so unit tests cover hit/miss behavior, TTL expiry, malformed entries, user scoping, duplicate prevention, and logout clearing.

How It Will Be Implemented

1. Shared GET caching

Add src/services/api/cache.js. It wraps Axios GETs, returns { data }, stores successful responses in sessionStorage, ignores failed responses, removes malformed entries, and dedupes identical in-flight requests.

2. Catalog store

Add src/stores/catalog.js. Vue pages stop calling stable catalog endpoints directly and instead ask the catalog store for subjects, courses, institutions, payment methods, and receiving institutions.

3. Chat session cache

Update src/stores/chat.js so room lists and recent room history are cached per user. Only confirmed server messages are stored; pending, failed, and temporary optimistic messages are excluded.

4. Backend incremental sync

Update backend/studybuddy/chat/views.py so history/?after_id=:id returns only newer messages. Normal history requests continue returning the latest 50 messages in the existing array shape.

Cache Behavior Rules

What can be cached

  • Stable catalog/reference data with practical TTLs.
  • First chat room page for quick revisit rendering.
  • Recent confirmed messages for each room during the browser session.

What should not be cached

  • Failed API responses.
  • Pending or failed optimistic chat messages.
  • Per-tutor mutable data such as /tutor/subjects/.
  • Anything that must survive logout or cross browser sessions.

Core Contracts

Frontend cache helper

  • cachedGet(url, options) returns a response-like { data } object.
  • Keys start with sb- and include scope, user id, normalized path, and params.
  • Failed responses are never stored, malformed entries are removed, and identical requests dedupe while in flight.

Backend chat history

  • GET chat/rooms/:roomId/history/ keeps the latest-50 array response.
  • ?after_id=:id returns newer messages only, ordered by id and capped at 50.
  • History queries include sender profile data to avoid extra serializer lookups.

Chat Revisit Flow

Fast path

When a user opens a room, cached messages appear immediately if present. The UI no longer has to wait for the full history request before showing recent conversation context.

Freshness path

The store connects the WebSocket, marks the room read, asks the backend for messages newer than the cached high-water mark, then reconciles by message id.

Risks To Watch

Stale chat state

Read receipts and unread counts can briefly show cached values until the background refresh lands.

Privacy on shared devices

Recent message bodies live in sessionStorage during the browser session, so logout and user-switch clearing must stay reliable.

Duplicate messages

Cached, REST, optimistic, and WebSocket messages must reconcile through stable ids and reuse existing replacement logic.

Mutation invalidation

Catalog and chat updates need explicit refresh or cache clearing where data can change underneath the TTL.
