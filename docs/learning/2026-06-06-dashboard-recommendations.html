Dashboard Recommendations: wiring the hybrid algorithm

How the tutee dashboard's "Try out these tutors" widget will start using StudyBuddy's real hybrid recommender — ranked by the tutee's course + profile subjects and tutor ratings — without making the dashboard slow. Covers the algorithm, the hidden bottleneck, the Redis caching layer, and exactly which files change. This explains the design before it's built.

The problem we're solving

The hybrid recommender already exists and works — but the dashboard widget doesn't use it. It shows a hard-coded stub.

What the widget shows today

# backend/studybuddy/views.py  -> student_dashboard()
tutors = Tutor.objects.all().select_related('profile')[:3]   # first 3 rows. that's it.
#WeaknessConsequence
1Returns the first 3 tutors in the tableNo subject match, no course match, no ranking. Same 3 for everyone.
2Ignores the tutee's profileAn IT student is not shown IT tutors. The widget teaches the user nothing.
3Ignores ratings entirelyThe collaborative-filtering signal (what similar students liked) is wasted.
4The real algorithm only runs in the booking flow/recommend-tutors/ is wired to FindTutors.vue, not the dashboard.
The goal Make "Try out these tutors" rank by the hybrid score — course + profile subjects (content) blended with tutor ratings (collaborative) — while keeping the dashboard fast at pilot scale (hundreds of tutors, thousands of tutees and ratings) and ready to scale further.

How the recommender works

Three pieces already live in backend/studybuddy/recommender/. The dashboard will reuse them unchanged in spirit.

📚 CBF — cbf.py

Content-based: compares the tutee's profile to each tutor (subject, expertise, course, year, level). Answers "is this tutor a good academic fit?"

⭐ CF — CF.py

Collaborative: finds students similar to you (Pearson similarity over ratings) and predicts how you'd rate this tutor. Answers "did people like me rate them well?"

⚖ Hybrid — hybrid.py

Blends the two into one score and ranks tutors high → low.

The blend (as it is in code today)

final = 0.70 × CBF  +  0.30 × (CF / 5)
Paper vs. code mismatch — noted, but out of scope here Your paper states 0.60 × CBF + 0.40 × CF. The code uses 0.70 / 0.30 and divides CF by 5 (CF predicts a 1–5 rating; the /5 rescales it to 0–1 so it's comparable to CBF). This wiring task does not change the weights — that's a separate decision you'll make about whether to align the code to the paper or the paper to the code.

How "course + subjects" drives the ranking

The CBF score is a weighted sum. Subject and course are the heaviest terms, which is why an IT student naturally sees IT-course tutors who teach their subjects at the top:

# cbf.py weights
W_SPECIFIC  = 0.40   # exact subject match
W_GENERAL   = 0.20   # exact or same-category match
W_EXPERTISE = 0.15   # how strong they are in the best matching subject
W_COURSE    = 0.10   # same course (0.5 partial credit for same strand)
W_YEAR      = 0.10
W_LEVEL     = 0.05

For the dashboard, subject membership becomes a hard filter (we only score tutors who teach one of your preference subjects), and course stays a score term (so same-course tutors rank highest). That matches what you asked for: "IT course → IT tutors at the top."

The hidden bottleneck

Before caching anything, there's a real inefficiency to fix — otherwise we'd just be caching over a slow path.

What happens now, per request

To score a tutor, CF needs your "neighbors" (the most similar students). But the neighbor set depends only on you — not on the tutor. The current code recomputes it once for every candidate tutor:

# hybrid.py (today): loops tutors, and INSIDE compute_cf_score...
for tutor in tutors:
    cf = compute_cf_score(ratings, student_id, tutor_id)   # -> top_k() recomputes
                                                           #    similarity to EVERY student
                                                           #    again, for each tutor
Cost: O(tutors × students × ratings) With 300 tutors and 3,000 students, the same neighbor calculation runs 300 times per dashboard load — 299 of them redundant. On the dashboard (loaded on every visit) that adds up fast.

The fix: compute neighbors once

# hybrid.py (fixed): hoist the student-only work out of the loop
neighbors = top_k(ratings, student_id)        # ONCE per request
for tutor in tutors:
    cf = compute_cf_score(ratings, student_id, tutor_id, neighbors=neighbors)

Same math, same results — cost drops to O(students × ratings) + O(tutors). This is a pure efficiency change with no effect on the scores, and we'll assert it with a test.

Caching: don't recompute what hasn't changed

Your recommendation only changes when your preferences change, a new rating lands, or a tutor is added. None of those happen second-to-second — so we compute once and serve a stored copy for a while.

The rules

SettingValueWhy
Cache keydash_recs:{tutee_id}One cached list per tutee.
TTL~600s (10 min)New ratings/tutors appear within ~10 min. Good enough for a "discover" widget.
Early bustOn preference saveIf you change what you want, the next load recomputes immediately — not after 10 min.
Why cache after the bottleneck fix, not instead of it Caching hides cost on repeat loads, but the first load and every load right after a preference change still compute live. Fixing the neighbor loop makes that live path fast too. Cache + fix together = fast always, not just fast-when-warm.

The tech stack — and why each piece

⚡ Redis

An in-memory key–value store. Reads/writes in well under a millisecond. Here it holds each tutee's precomputed recommendation list.

📦 Django cache framework

Django's built-in cache.get/set/delete API. Our code talks to this, not to Redis directly — so the backend is swappable.

🔧 RedisCache backend

Django 6 ships django.core.cache.backends.redis.RedisCache — no extra Python package needed. Just point it at a REDIS_URL.

🧮 The recommender package

Existing cbf.py / CF.py / hybrid.py. We add a thin dashboard.py service on top.

Why Redis (and the honest tradeoff)

Redis chosenDB cache tableIn-memory (LocMem)
SpeedFastestOne indexed row readFastest
Shared across workersYesYesNo — per process
New infrastructureYes — a Redis serverNo (uses your DB)No
Scales to CExcellentOKPoor
The tradeoff you accepted Redis is this project's first Redis dependency — django-q2 was deliberately kept on the DB broker to avoid it. The payoff: the same Redis can later back the background precompute job (C-scale) and a real-time chat layer. The cost: a Redis server must be running and reachable, configured via REDIS_URL.

Why not just hit the database harder?

The expensive part isn't a DB query — it's the Python computation (similarity math across thousands of ratings). A DB index can't cache the result of a calculation. Redis can: we store the finished, ranked list and skip the math entirely on a hit.

How it's going to be built

One new service function is the spine. The dashboard view (now) and a future background job (later) both call it — that's the B→C bridge.

The data flow, per dashboard load

# the one entry point everything goes through
def get_dashboard_recommendations(tutee, limit=10):
    key = f"dash_recs:{tutee.id}"
    cached = cache.get(key)
    if cached is not None:
        return cached                          # HIT: instant

    subjects = get_student_subject_codes(tutee)   # from their Preference
    candidates = tutors_teaching(subjects)        # hard filter
    ranked = recommend_tutors_hybrid(             # neighbors computed ONCE inside
        build_rating_matrix(), tutee, requested_subject=None,
        candidate_qs=candidates)
    data = serialize(ranked[:limit])              # {id,name,rating,subjects,hourlyRate}
    cache.set(key, data, timeout=600)
    return data

Build order (sequential — no parallel agents)

#Step
1Fix CF/hybrid: compute neighbors once, pass them in. Add a test proving it.
2Add recommender/dashboard.py with get_dashboard_recommendations (+ cold-start fallback).
3Configure CACHES (RedisCache) in settings.py; add REDIS_URL to .env.example.
4Wire student_dashboard to call the service (keep the JSON shape identical).
5Bust the cache key in the preference-update endpoint.
6Tests: neighbor-once, cache hit/miss, bust-on-save, Redis-down, cold start. Run manage.py check + npm run build.
The frontend doesn't change Dashboard.vue already reads recommendations from GET /dashboard. As long as the backend keeps the { id, name, rating, subjects, hourlyRate } shape, the widget just starts showing better tutors with zero Vue edits.

Edge cases & resilience

SituationBehaviour
Redis is down/unreachableThe service catches the cache error, logs a warning, and computes directly. The dashboard never 500s because the cache is offline — it just loses the speed-up.
Tutee has no preference subjects (cold start)Fall back to a simple recent/any-tutor list in the same JSON shape, so the widget is never empty.
No ratings anywhere / student not in matrixCF returns None → contributes 0; CBF still ranks by course + subject. Confirmed by a test.
New rating arrivesReflected on TTL expiry (≤10 min). Acceptable for a discover widget; not the login critical path.
The trap we avoid A naive "cache forever" would freeze recommendations — a student who fixes their profile would keep seeing the old, wrong tutors. The TTL + bust-on-preference-save keeps the widget honest without recomputing on every single page view.
Scaling to C, later (no rewrite) Because all the work lives behind get_dashboard_recommendations, the C-scale upgrade is additive: a django-q2 scheduled job calls that same function for active tutees every N minutes and warms Redis ahead of time. The dashboard then only ever reads a hit. Nothing in the view or the frontend changes.
