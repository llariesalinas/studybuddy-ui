1 Scope

Two independent pieces of recent work, unrelated to each other except in timing:

  • Instant Booking — replaces the old request-to-book flow (tutor manually accepts/rejects) with instant confirmation. Design is finalized (ADR 0008); backend and most of the frontend shipped; a few UI pieces are still open — see section 3.
  • Subjects — the course catalog went from per-institution to one global list, and tutors can now propose subjects missing from it during onboarding. Both fully shipped.

2 Instant Booking — what changed

Old flow: tutee sends a booking request → sits Pending → tutor manually approves or rejects it. New flow: a slot inside a tutor's published availability confirms immediately on submission — no tutor review step at all.

Why
Panel feedback asked for the manual confirmation layer to be cut entirely. The trade-off: tutors lose per-tutee vetting before commitment; the replacements are an auto-opened chat thread and a real cancellation window instead of a pre-booking gate.

The new mechanics

  • Grace Cutoff (12h): cancel before it, free and untracked, for either role. Cancel after it (a Late Cancellation) and the booking still cancels immediately — never blocked — but it auto-opens a Support Ticket for an admin to review.
  • Counted Strike: admin resolves a Late Cancellation ticket as Excused or Counted. Counted deducts a flat ₱50 from a tutor's wallet (tutees have no wallet, so no fee). Both roles share a Monthly Strike Cap of 3 — hitting it suspends booking (tutee) or search visibility (tutor) for the rest of the calendar month.
  • Booking-time gates: the three checks that used to run when a tutor accepted a request (verification/renewal, non-negative wallet, session load limit) now run at booking creation instead. A tutor failing any of them is simply hidden from search — no more "accept and then get blocked."
  • Booking Horizon (14 days): a session can't be booked more than 14 days out, to cap the damage from stale recurring availability now that there's no approval step to catch it.
  • Meeting Link: Online sessions get a server-generated Jitsi room link at booking time, no manual scheduling.
Removed outright
The old approve_booking/reject_booking endpoints and the tutor's "Requested Sessions" screen are gone, not deprecated. Pending survives only as a historical status on old rows — nothing new is ever created in it.

3 Instant Booking — shipped vs. remaining

Backend is fully in place and reviewed. A few frontend surfaces are still open.

Shipped

  • Instant confirmation, all three booking-time gates, Booking Horizon, Meeting Link generation
  • Grace Cutoff cancellation, Late Cancellation ticket auto-open, admin excused/counted resolution with wallet/strike effects
  • Search-visibility extended for negative wallet, load limit, and strike-cap suspension
  • approve/reject endpoints + Requested Sessions screen removed; existing Pending bookings auto-expired with a rebook notification
  • Booking confirmation screen shows the Meeting Link/location and cancel deadline; 14-day horizon enforced in the date picker
  • Tutor dashboard banner explaining load-limit invisibility

Still open (tracked as Fix round 1 on the same brief)

  • Tutors have no cancel button yet — only tutees can cancel a session from the UI today
  • Admin support queue has no Excused/Counted control for Late Cancellation tickets yet
  • Tutor Management doesn't show a tutor's monthly strike count yet
  • No test coverage yet for the Grace Cutoff cancellation, strike accounting, or the new search-visibility gates (the code is in and manually verified correct; automated coverage is the gap)

4 Subjects — one global catalog

The course/subject catalog used to be scoped per institution. It's now a single global list — one CRUD surface (AdminCourseCatalog.vue) instead of duplicated per-institution catalogs, alongside removing the now-meaningless institutional-Admin-promotion workflow left over from the SuperAdmin role consolidation.

5 Subjects — tutors can propose their own

Landed as part of the tutor onboarding & verification redesign. During onboarding, a tutor searches the catalog first; if what they teach isn't listed, they can propose it as a new subject (capped at 8 subjects total across approved + pending).

  • Independent per-subject review: an admin approves or rejects each proposed subject on its own, separate from the tutor's overall application decision — in AdminTutorApplications.vue's new "Proposed Subjects" list.
  • No recognition check on proposals — a tutor can propose something not yet in the catalog by definition; recognition checks only apply to subjects a tutee books.
Known follow-up, not yet ticketed as urgent
Typos or missing categories in a tutor-proposed subject (e.g. "pYTHones", or a subject with no field/category set) degrade recommendation quality slightly but never break it — flagged as a separate data-hygiene/admin-edit follow-up, not a blocker.
