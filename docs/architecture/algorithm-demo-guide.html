Algorithm demo guide

How to enable, log into, and exercise the SuperAdmin Algorithm Demo page — the tool that runs the real hybrid recommender (CBF + CF) against seeded data. Covers both the mechanics (flag, gate, routes) and the curated personas whose scenarios prove each part of the scoring. Every score below was read from the seeded database on 2026-07-16, not hand-calculated — rerun the seed with its fixed random seed 20260716 and these numbers reproduce exactly.

Quick facts

Where

SuperAdmin panel → /superadmin/algorithm-demo. Ranked List and Compare Pair tabs.

Gate

IsAuthenticated + IsSuperAdminUser, plus ALGORITHM_DEMO_TOOLS_ENABLED — checked first, 403 when off.

Data

Runs the real hybrid.py recommender against whatever is currently seeded — not a mock or a fixture.

Scope

Unscoped by institution by default (any subject-matching tutor). An optional institution filter narrows it.

Enabling the tool

The flag defaults to OFF everywhere and must be explicitly turned on per environment.

Local dev

  1. In backend/.env, set ALGORITHM_DEMO_TOOLS_ENABLED=true.
  2. Restart Django: cd backend && venv\Scripts\python.exe manage.py runserver.
  3. Log in as SuperAdmin (superadmin@studybuddy.test, password studybuddy123) and open /superadmin/algorithm-demo.

Demo deployment (Render)

  1. Render dashboard → studybuddy-demo-backend service → Environment tab.
  2. Add ALGORITHM_DEMO_TOOLS_ENABLED = true. Saving auto-redeploys.
  3. Log in on the demo frontend as a promoted SuperAdmin and revisit the page.

Render env vars are not read from any .env file — they live in the Render dashboard only. If the page shows "Algorithm demo tools are disabled on this backend," the var was never added there.

Per the demo deployment plan, this flag should stay ON for the protected demo environment (defense/testing) and OFF for any future real production deployment.

Before you start: reset the demo data

From backend/, run venv\Scripts\python.exe manage.py reset_demo_data && venv\Scripts\python.exe manage.py seed_data. Local/dev only, destructive: wipes all Tutee/Tutor users and reseeds the curated personas below plus filler population with a fixed random seed (20260716) — same result every run. Admin and SuperAdmin logins are never touched.

Admin & SuperAdmin logins preserved across every reset_demo_data run

These accounts are never created or overwritten by reset_demo_data — they must already exist. Use them for the SuperAdmin gate above, or to cross-check institution-scoped data around the same curated tutors/tutees.

Who to demo with two accounts carry the whole story

Eight of the ten tutees (S2, S3, S4, S6, S7, S8, S9, S10) form the tier-1 programming core: BSCS students who co-rate an overlapping set of five tutors (T1, T2, T6, T7, T8). That overlap is the point. Pearson similarity is computed only over tutors both students have rated, so a pair sharing one tutor scores 0 and is dropped entirely, and a pair sharing exactly two always scores exactly ±1 whatever the values are. Three or more shared tutors is what makes similarity a real number rather than a wall of 1.00. seed_data asserts this on every run and refuses to finish if it is violated.

S6 Katrina Katigbak The CF protagonist. Five ratings given, four contributing neighbours on T1 with similarities spread from +0.308 to +0.970, and one neighbour (S4) who rated T1 below her own average and so pulls the score down. She has also rated T1 herself, so the panel can compare CF's prediction of 4.742 against her actual 5.
S1 Felipe Fernandez The Cold-Start showcase. Deliberately has no ratings at all, so he is absent from the rating matrix and every candidate returns cold_start: true with CF contributing nothing. Ranking falls back entirely to the 70% CBF term.

Two moments worth pointing at on S6's board, both emergent from the data rather than staged: T6 Fidel Fajardo outranks T1 (0.949 vs 0.927), so the top of the board is a genuine contest; and a filler tutor holds the highest CBF of the entire pool (0.935) yet falls to 4th because no peer has rated him — the clearest available illustration of what the CF term actually buys.

S5 Jacinto Jimenez (BSBA) sits outside the core as a non-BSCS control, and like S1 gives no ratings. T3/T4/T5 are rated only by non-BSCS filler cohorts, which is why T4 and T5 appear in S6's candidate list with no peer signal and fall through to the global pool.

Walkthrough

Ranked List tab

  1. Pick a tutee (e.g. S6 Katrina Katigbak) from the searchable dropdown.
  2. The top-5 comparison table shows every weight side by side — each cell carries the sub-score with its weighted contribution beneath it, shaded so the weights that carried the ranking stand out.
  3. Below it, every subject-matching tutor ranked by Hybrid Score.
  4. Click any row, in the table or the list, to open its CBF bars and the CF waterfall.
  5. In the waterfall, click a neighbour's N co-rated chip to expand the shared ratings behind its similarity — see “Co-rated set” below.

Compare Pair tab

  1. Pick a tutee, then a tutor (e.g. S1 Felipe Fernandez → T1 Marisol Aquino, then S1 → T5 Esperanza Elizalde).
  2. See stat cards for both sides: subject preferences/expertise and tutor rating history.
  3. Watch the same animated CBF/CF/Hybrid breakdown, side by side.

Co-rated set where a similarity comes from

Each neighbour row carries a N co-rated chip. Click it to expand the tutors both students rated, with each student's score for every one of them and the average taken over just those tutors. The similarity meter above stops being a number to take on faith: the expanded cells are the inputs Pearson ran on, and a panelist can check them by hand. One neighbour opens at a time, and the cells are read-only — the neighbour's rating slider stays the only control.

Two different averages are on screen, and they are labelled. The one inside the expanded panel is taken over the co-rated set only, because that is what Pearson measures deviation from (CF.py, sim). The avg on the collapsed row is the neighbour's mean over all their ratings, which is what the deviation term uses. They are different numbers whenever a student has rated a tutor the other has not — and the divergence usually shows up on the tutee's side, not the neighbour's. On the curated cast, S6 Katrina Katigbak has a different average against every neighbour she is compared with (4.25 vs S2, 3.75 vs S3, 3.50 vs S4, 3.80 vs S10), none of which is the 3.80 baseline the prediction actually starts from.

Values move on a reseed. The pattern is the durable part: expand S4 Imelda Ignacio on T1, the lowest-similarity contributing neighbour, and her shared ratings show why she barely counts and why she drags the prediction down — she rated T1 below her own average while the other three rated him above theirs. Design recorded in the co-rated set mockup.

What-if rating edits nothing is saved

Each contributing neighbour row carries a 1–5 slider. Dragging it re-runs the real recommender on the server with that rating overridden in memory — the rating matrix is patched in apply_rating_overrides before neighbour selection, and nothing is ever written to the database. The frontend does not recompute anything itself, so there is no second implementation of the algorithm to defend.

  1. Select S6 Katrina Katigbak, then T1 Marisol Aquino.
  2. Drag S10 Olivia Ocampo's rating down. Her deviation segment shortens and flips direction, the CF score falls, and the Hybrid Score follows.
  3. Watch the top-5 table re-sort underneath — T1 can lose its place outright.
  4. A “What-if — nothing saved” chip appears with a Reset button that discards every override and refetches the stored data.

Similarity normally holds still while you drag, and that is correct: Pearson is computed over tutors both students rated, and the tutee has usually not rated the candidate. The exception is a candidate the tutee has rated — T1 for S6 — where the tutor sits inside the co-rated set and the similarity meters do move. Those rows are labelled.

Gated by the same ALGORITHM_DEMO_TOOLS_ENABLED flag as the rest of the page. See the CF clarity plan; the earlier live rating edit design doc describes the superseded save-to-database behaviour.

Things to know

  • The candidate pool is unscoped by institution by default — any subject-matching tutor, any institution. An institution filter (defaulting to "All institutions") narrows both the tutee picker and the tutor candidate pool.
  • Changing the institution filter while a tutee is selected clears that selection, since it may no longer be valid under the new scope.
  • Curated surnames run alphabetically (Aquino → Ocampo) so they're easy to spot in the filler population by eye.
  • Similarity is computed over the co-rated intersection only. Fewer than 3 shared tutors makes it meaningless — 1 shared scores 0 and drops the neighbour, 2 shared always scores exactly ±1 — so any neighbour row below that threshold is labelled in the UI, and seed_data refuses to finish if a tier-1 pair falls under it.
  • The candidate pool does not exclude tutors the tutee has already rated, matching both production paths. That is what makes the prediction-vs-actual accuracy check possible on S6 → T1.
