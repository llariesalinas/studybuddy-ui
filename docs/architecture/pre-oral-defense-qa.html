How do you handle the secondary vs. tertiary distinction?

A tutor declares a teaching level, and the content-based recommender applies a matching penalty when a tertiary tutee is scored against an SHS-only tutor. That's a match-quality signal inside the recommendation score, not a hard access-control wall the way institution scoping is.

Objective 2 · Hybrid Recommendation Module Fully built

"To design a Hybrid Recommendation Module that uses Attribute-based and User-user collaborative filtering to match tutees with compatible peer tutors."

Walk us through the hybrid score.

hybrid_score = 0.7 × CBF_score + 0.3 × (CF_score / 5). CBF is a weighted sum of five sub-scores â€” subject match, tutor expertise, course match, year-level proximity, and teaching-level fit. CF is classic user-user collaborative filtering: Pearson correlation between tutees over co-rated tutors, top-5 neighbors, mean-centered weighted prediction.

30-second answer: We combine two ideas: how well the tutor fits the student's profile, and how students with similar rating behavior responded to that tutor. Profile fit has the bigger share.

Why 70/30 â€” are those weights tuned or learned?

They're fixed constants set by design judgment, not learned from data or A/B tested. We don't have enough real usage history yet to run that kind of tuning, and we're upfront that this is scoped as future work rather than a finished calibration.

30-second answer: The 70/30 means we give more importance to academic and profile fit, and less to rating history. We chose that balance manually for now.

What happens for a brand-new tutee with no rating history?

CF reports a cold-start state, and the hybrid formula treats that as zero rather than reallocating its 0.3 weight back into CBF â€” so a cold-start tutee's score caps at 0.7×CBF. That's an intentional, documented simplification.

30-second answer: A new student can still get recommendations. The system simply relies on profile fit first until rating history exists.

Did you use a machine-learning library for this?

No â€” both CBF and CF are hand-written in plain Python; there's no numpy, pandas, or scikit-learn in the dependencies. That was a deliberate choice for transparency: we built a staff-only "Algorithm Demo" tool specifically to show the CBF sub-scores and the CF neighbor computation live, for a real tutee/tutor pair, on request.

30-second answer: No. We built the recommendation logic ourselves so we can explain every part of it clearly.

How does a tutor set their availability?

A recurring weekly grid of day + 30-minute slots, plus one-off overrides for a specific date â€” blocking the whole day or a single slot for something like a holiday or personal conflict. A tutee sees a real month calendar of a specific tutor's open slots, merged live from the recurring template, active bookings, and overrides.

What does "assesses assigned workloads and limitations" actually mean in the running system?

Every tutor has a session-load limit (default 10, admin-adjustable 1–20). We count their currently accepted or awaiting-payment sessions, one commitment per session group, and block them from accepting anything new once they hit that number. It's a hard counter-and-cap, not a load-balancing or optimization algorithm â€” we didn't build auto-suggestion of alternate tutors or predictive workload forecasting.

30-second answer: It means the system counts how many active sessions a tutor already has and stops new ones once that limit is reached.

What stops two tutees from double-booking the same slot?

Two layers, in the order they actually fire. First, the booking-confirmation view takes a database row lock (select_for_update()) on the specific availability slot inside a transaction â€” if two tutees submit near-simultaneous requests for the same slot, the second one blocks until the first commits, then correctly sees the slot as already taken and gets a clean error instead of creating a duplicate. Second, a database-level unique constraint on the availability/date pair is the backstop in case any other code path ever creates a booking without going through that locked view. It's important that tutor approval isn't the thing preventing this â€” by the time a tutor reviews a `Pending` request, that request has already won the race; tutor review is a business decision, not a concurrency mechanism.

30-second answer: Once one student gets a slot, the system locks it so another student cannot take that same time.

Is any of this real-time â€” does a tutee see a slot disappear the instant it's booked?

No â€” chat is the only real-time channel in the app (a Django Channels WebSocket); everything else, including availability and booking state, is pull-based: fetched on page load and re-fetched only after an explicit user action. That means a tutee's screen can show stale availability for a moment. It does not mean stale UI can produce a double-booking â€” the row lock above resolves that deterministically at the backend regardless of what any open tab happens to be displaying. We'd frame this precisely if asked: the UI isn't real-time, but the concurrency guarantee doesn't depend on it being real-time.

30-second answer: The screen is not live-updating, but the backend still prevents double-booking even if two people briefly see the same slot.

Objective 4 · Compensation Module Fully built

"To implement a Compensation Module that calculates payments based on the total number of completed peer tutoring sessions."

How is a tutor's pay actually calculated?

The moment a session is marked Completed, the system applies a flat 10% platform commission. For online-paid sessions, the tutor's wallet is credited the remaining 90% directly. For cash sessions â€” where the platform never touches the money â€” the same 10% is instead debited from the tutor's wallet balance, so the net effect matches either way.

30-second answer: When a session is completed, the platform keeps 10% and the tutor gets 90%.

Is the rate the same for every tutor?

Yes â€” flat 10% across the board. No tiered or performance-based rate, no per-subject or per-institution rate. That's a deliberate simplicity choice for this version of the system.

Since cash sessions debit commission straight from the tutor's wallet, can a tutor actually go into debt?

30-second answer: Yes. If cash-session commissions make a tutor's wallet go negative, they are blocked from accepting more bookings until it is settled.

How does a tutor get their money out, and is it real money?

Beyond the five objectives · Student Safety & Protection Built, but manual & human-reviewed

30-second answer: During the session, the app asks the student to check in, and if they report a problem it opens support right away.

Why is the location just a typed-in text field instead of an actual map â€” pinning a location, geocoding, showing it on Google Maps?

Cost. General system Q&A

architecture, security, testing, deployment

Architecture

What's the stack, end to end?

Vue 3 + Vite + Pinia on the frontend, deployed to Vercel. Django 6 + DRF + Channels/Daphne on the backend (Channels only for the chat feature's WebSocket layer), deployed to Render. PostgreSQL is hosted on Supabase, reached through its session pooler because Supabase's direct-connection host is IPv6-only and Render has no outbound IPv6. Redis is used for caching and channel layers when configured, falling back to in-memory for a single-instance deployment like the demo.

30-second answer: The frontend is built with Vue, the backend is built with Django, and the data is stored in PostgreSQL.

Is anything in the system actually real-time, and what stops two people from racing for the same thing?

Only chat â€” a Django Channels WebSocket, which is the single push channel in the app. Everything else, including tutor availability and booking state, is pull-based: fetched once on page load and again only after an explicit action, not pushed live. That means a tutee's screen can briefly show stale availability. It does not mean two tutees can double-book the same slot: the booking-confirmation view takes a database row lock on the specific slot inside a transaction, so a second near-simultaneous request blocks until the first commits, then correctly sees the slot as taken. A database-level unique constraint backs that up in case any other code path ever bypasses the locked view. Tutor approval is not what prevents the race â€” by the time a tutor reviews a request, it has already won.

30-second answer: Only chat is real-time. Booking is not live-updating, but the backend still prevents two people from taking the same slot.

Security

How is authentication handled?

JWT via SimpleJWT â€” 5-minute access tokens, 7-day refresh tokens, with rotation and blacklisting on every refresh. The frontend silently refreshes every 4 minutes, comfortably inside that window, and force-logs-out after 10 minutes of inactivity independent of token expiry. Registration is domain-locked to each institution's verified email domain.

30-second answer: Users sign in with token-based sessions, the app refreshes those sessions automatically, and inactive users are logged out.

Do you have two-factor login?

Yes â€” email-based OTP on login, rate-limited against brute force. It's disabled specifically on the demo deployment because Render blocks outbound raw SMTP and we don't yet have a verified domain for an HTTPS email API; the full flow is active locally and would be active in a real production deploy with email configured.

30-second answer: Yes, through an email OTP, but it is turned off on the demo deployment because that host cannot send our emails.

Testing

What's actually covered by automated tests?

35 backend test classes covering recommendation/matching, wallet and payments, verification and applications, chat, and auth â€” run against a real Postgres instance in CI on every pull request. On the frontend, 15 Vitest files cover stores, components, and composables, with lint and build also run in CI. There's no quantitative coverage percentage tool wired in, so we can speak to what's tested, not a coverage number.

30-second answer: We have automated tests for the main backend flows and key frontend pieces, but we do not currently report a single coverage percentage.

Demo deployment

Is what we're demoing today production-representative?

Mostly, with a few infrastructure-driven exceptions unique to the free-tier demo host: the whole demo site sits behind a shared Basic Auth gate (with uploaded media exempted so images still load), all outbound email is suppressed because Render blocks raw SMTP, and cash-out payouts are simulated because PayMongo's sandbox has no live payouts product. None of these are algorithmic or feature limitations â€” they're deployment-environment workarounds, and each is behind an explicit flag that can't leak into a real production deploy.

30-second answer: Mostly yes, but the demo has a few temporary limits like shared login protection, no outgoing email, and simulated payouts.

Recurring/repeat bookings, file or material sharing inside chat, and dispute/refund handling are all genuinely not started. A built payment screen (PaymentScreenTutee.vue) also isn't wired into the live booking flow, which currently confirms a booking without an intermediate payment step. We'd frame all of these as deliberate scope boundaries for this defense cycle, not oversights.

30-second answer: Repeat bookings, file sharing in chat, and full dispute or refund handling are still outside this version.
