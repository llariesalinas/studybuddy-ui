Requests is conditional and self-retiring. Per ADR 0008 (Instant Booking), Pending bookings can no longer be created - the live path sets status='Confirmed' at views.py:2670. The subsection renders only when legacy Pending rows exist, so they are not stranded, and disappears once they age out. It has no cap and no expander: the uncapped-requests state those would have guarded against is unreachable. Payments is never capped. Andrea and Kim appear in both columns by design - they are committed time and carry an outstanding payment action. Josh, Bea and Ivan are requests, so they appear in the rail only - an unaccepted request is not committed time and must not read as a scheduled session.

Routing rules

BookingRailScheduleWhy
raw_status = Pending
(legacy rows only)		Requests— A request, not a commitment. Showing it in the schedule would overstate the tutor's booked time. No longer generated - see the note above.
display = Payment Required
(Confirmed, past end time)		PaymentsYes Committed time that already happened, with an action still owed. Pagination would otherwise bury it as days pass.
raw = Awaiting Payment Verification
(displays as Awaiting Verification)		PaymentsYes Committed time holding a real slot, with money outstanding.
display = Upcoming / Ongoing
(Confirmed)		—Yes Nothing owed. Ongoing needs no pinned bar - the global OngoingBookingBar already docks it app-wide.
Everything routes on raw_status except the Payments bucket, which routes on the derived status. This matters: display_status is rewritten to "Payment Required" when BOOKING_DEV_TOOLS_ENABLED is on, so routing the other buckets by display value would shift behaviour between environments.

Pagination

RuleDetail
SideClient-side. The endpoint already returns every upcoming booking and groups them server-side, so paginating in Django would still fetch the whole queryset. No backend change.
UnitDay-packed: accumulate whole days toward a target of 6 bookings, never splitting a day across pages. Always take at least one day, so a single heavy day gets its own page.
ScopeSchedule only. The rail is capped + expandable instead, so there is never more than one pager on screen.
LabelActual range, e.g. "Showing 1-5 of 9" - page sizes vary because pages break on day boundaries.
